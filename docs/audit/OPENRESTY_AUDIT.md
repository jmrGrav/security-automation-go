**Date:** 2026-06-12  
**Scope:** OpenResty integration — ban enforcement, event ingestion, Lua bouncer, health vs dashboard discrepancy

## Executive Summary

OpenResty is running and the ban enforcement path (Lua bouncer) is functional. However, the event reporting path (`events.jsonl`) is completely inactive, and there is a visible discrepancy between the Dashboard ("WAF events") and the Health page which correctly shows the events file as missing.

## OpenResty Integration Architecture

```
CrowdSec active bans
    ↓ pushLuaState() — every daemon tick
/run/crowdsec-lua/bans.json         ← ✅ EXISTS (Lua bouncer reads this)
    ↓
OpenResty Lua bouncer (ngx_lua)
    ├── blocks IPs in bans.json      ← ✅ enforcement active
    └── writes events.jsonl          ← ❌ NOT CONFIGURED / NOT WRITING

/run/crowdsec-lua/events.jsonl       ← ❌ DOES NOT EXIST
    ↓
openrestyevent.LiveSource.Read()
    └── os.Stat() → not found → return nil, nil
        ↓
wafRuntime.processOpenResty() → 0 events per tick → 0 reports to AbuseIPDB
```

---

## State of `/run/crowdsec-lua/`

```
/run/crowdsec-lua/
├── bans.json       ✅  — written by pushLuaState() each daemon tick
└── events.jsonl    ❌  — NOT PRESENT
```

`bans.json` is the ban list consumed by the Lua bouncer to block IPs at the nginx layer. Its presence confirms:
- OpenResty/nginx is installed and running
- The Lua bouncer module is loaded
- `pushLuaState()` is running correctly (LuaStatePushEnable = true)

`events.jsonl` would contain WAF-level detections generated by the Lua security rules (honeypot hits, score-based detections). It is written by a separate Lua module that must be explicitly configured in nginx.

## Dashboard vs Health Discrepancy

### Dashboard (`/`) — shows "OpenResty active (WAF events)"

```go
// internal/ui/server.go:946
func openRestyDashboardDetail(detectors []detect.Result, eventsFile string) string {
    for _, d := range detectors {
        if d.Name == "openresty" {
            if d.Healthy {
                if strings.TrimSpace(eventsFile) != "" {
                    return "OpenResty active (WAF events)"  // ← shown when eventsFile configured
                }
                return "OpenResty active (nginx log mode)"
            }
        }
    }
}
```

Condition: OpenResty detector says `Healthy=true` AND `cfg.OpenResty.EventsFile != ""`.  
The dashboard does NOT check whether the events file actually exists.

### Health page (`/health`) — shows YELLOW "Events file configured but missing"

```go
// internal/health/checks.go:175
func CheckOpenResty(cfg Config) Check {
    if _, err := os.Stat(cfg.OpenRestyEventsFile); err != nil {
        return Check{
            Name:   "openresty",
            Status: Yellow,
            Reason: "Events file configured but missing: " + cfg.OpenRestyEventsFile,
        }
    }
    return Check{Name: "openresty", Status: Green, Reason: "Events file present"}
}
```

The health check DOES verify file existence. It correctly reports YELLOW.

### Root cause of discrepancy

The dashboard uses `detect.Result.Healthy` (OpenResty service is running → `true`) plus `eventsFile != ""` (path is configured → `true`). It conflates "OpenResty running" with "WAF events available". The health check is more precise: it checks whether the file exists.

**Fix needed:** The dashboard detail should check `os.Stat(eventsFile)` before displaying "WAF events" text, or use the health check result instead of the independent detection result.

## OpenResty Lua Bouncer Integration

### Ban enforcement path (✅ Working)

Config `internal/config/config.go`:
```yaml
openresty:
  lua_state_path: /run/crowdsec-lua/bans.json
  lua_state_push_enabled: true   # ← set to true
```

`pushLuaState()` (`internal/app/runtime_helpers.go:103`) runs each daemon tick:
1. Fetches active CrowdSec bans
2. Applies shield + allowlist filters
3. Loads active CIDR bans from `cidr-banned.json`
4. Writes consolidated ban list to `bans.json`

The Lua bouncer reads `bans.json` at request time to decide whether to block an IP.

### Event ingestion path (❌ Dead)

Config:
```yaml
openresty:
  events_file: /run/crowdsec-lua/events.jsonl  # ← path configured
```

The `events.jsonl` is expected to be written by a Lua module installed in nginx that:
1. Runs scoring rules on each incoming request
2. Appends JSON events to `/run/crowdsec-lua/events.jsonl` when score threshold is met
3. Records honeypot hits directly

This module is NOT present in the current nginx/OpenResty configuration. The Lua bouncer (crowdsec-lua) only reads `bans.json`; it does not write `events.jsonl`.

**Event format expected** (`internal/adapters/openrestyevent/live.go`):
```json
{"ts": 1749600000.0, "type": "score_exceeded", "ip": "1.2.3.4", "score": 15, "detail": "/admin/config.php"}
{"ts": 1749600001.0, "type": "honeypot_hit",   "ip": "5.6.7.8", "score": 10, "detail": "/wp-admin/install.php"}
```

Fields: `ts` (Unix float), `type` (event type → becomes `ruleName`), `ip`, `score`, `detail` (URI → becomes `URIs[0]`).

## OpenResty Log Path (Alternative)

If `events.jsonl` is not available, CrowdSec events can still be enriched via nginx access logs (`NginxLogDir = /var/log/nginx`). This path IS configured and is used by `crowdsecevent.LiveSource.lookupURIs()` to correlate banned IPs with their recent request URIs.

However, this is a CrowdSec-event enrichment path, not a standalone OpenResty event source.

## No WAF Event Ingestion: Impact

Without `events.jsonl`, the entire OpenResty event pipeline is inactive:
- Zero OpenResty events in scoped SQLite DB
- Zero AbuseIPDB reports from OpenResty source
- Nginx-level detections (honeypots, score-based rules) are enforced locally but never reported externally

## How to Restore OpenResty Event Ingestion

1. Install a Lua script in nginx that writes to `/run/crowdsec-lua/events.jsonl` in the expected format.
2. Ensure the script has write access to `/run/crowdsec-lua/`.
3. Confirm the file appears: `ls -la /run/crowdsec-lua/`.
4. The health check will turn GREEN automatically once the file exists.
5. The daemon will start processing events within 60 seconds.
